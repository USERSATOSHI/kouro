Your task. Your workflow.

A Kouro workflow is a TypeScript declaration of agents, tools, inputs, and control flow. Build the graph once; the host validates it and records its execution.

1. Set up your project

This guide follows the current source checkout. The native tool changes described below are not in the published 2.0.9 runtime yet; rebuild the CLI from the checkout to use them.

Install Bun 1.3.14 or newer, Git, and Kouro. Model-backed runs also need an authenticated harness. The published packages are available from the Kouro package registry:

Terminal
bun add --global kouro --registry https://git.usersatoshi.com/api/packages/kouro/npm/
kouro --help

# From the project you want agents to work on:
kouro create template develop --template feature

This creates editable files under .kouro/develop/. Keep prompt text and schemas beside kouro.ts as the shipped starters do. For TypeScript editor support in your own project, install the authoring package:

Terminal
bun add --dev @kouro/core --registry https://git.usersatoshi.com/api/packages/kouro/npm/

The host supplies @kouro/core when loading workflow files; the development dependency lets your editor resolve its public types. Workspace-backed execution requires a Git repository with a committed HEAD. Commit the files workers must inherit; changes are made in private worktrees.

2. Declare inputs, agents, and a result

Create a WorkflowBuilder, give it a stable ID, declare its input, and wire a start node to a terminal node. Export the built definition as the default export:

{{firstExample}}

startAt chooses the entry. sequence connects success outcomes. complete ends execution and can expose an artifact as the run result. Creating an agent handle does not execute a model while the file loads.

3. Pass structured outputs between steps

artifactType<T>(id, schema) combines a TypeScript type with runtime JSON Schema. An agent with produces: Plan returns a validated artifact; plan.output binds that artifact to another node's input.

The generic type helps your editor; JSON Schema governs runtime validation. Keep them consistent, require the fields downstream agents need, and ask the agent to return the declared shape.

The practical examples use plans with steps, acceptance criteria, evidence, and risks. Changes and research reports have their own shapes. A command node already returns a standard result containing its exit code and output; use check.output as repair feedback.

Every invocation starts with its supplied context. Pass relevant artifacts explicitly rather than assuming a shared model conversation.

4. Choose a harness, model, and permissions

Set harness and modelId on an agent to pin its execution. Available public harness IDs are codex, claude, pi, and opencode. Authenticate and choose a model available through that harness. Explicit per-node choices take precedence over a run's default execution profile.

Agent options
workflow.agent("researcher", {
  harness: "claude",
  modelId: "YOUR_AVAILABLE_MODEL",
  prompt: "Research the task and cite primary sources.",
  input: { task },
  capabilities: [CAPABILITY.REPOSITORY_READ, CAPABILITY.NETWORK_ACCESS],
});
GrantPurpose
REPOSITORY_READRead repository context.
REPOSITORY_WRITEAllow changes in the invocation's working directory.
TERMINAL_EXECUTEAllow native terminal tools or an explicitly trusted command node.
NETWORK_ACCESSEnable native Codex live search/network access and Claude search/fetch tools.

Claude uses its native tool preset. Pi exposes its installed registry, with edit/write and Bash following grants; the base Pi toolset has no dedicated web search. Codex keeps its native tools and configures search from the network grant. Declared Kouro subagents remain read-only and cannot browse, edit, or spawn more agents. Codex may use sandboxed shell commands to read repository context; child requests for broader terminal access are declined. Native delegation is disabled for Codex and Claude so child work follows .subagent.

Tool presence and successful retrieval are different: provider configuration, credentials, and installed extensions still matter. Kouro currently exposes typed capabilities, rather than a public per-tool tools option. OpenCode uses its external CLI configuration; the Codex/Claude/Pi tool policies described here do not configure it.

terminal.execute authorizes trusted commands. Pi Bash and explicitly trusted command nodes run without Kouro OS containment; configure them for projects whose code and scripts you trust. Dependency installation needs access to the required registry. A private worktree begins from committed files, so install dependencies there before checks.

5. Connect decisions and bounded repairs

An approval node pauses on durable operator review. Connect approved, rejected, and changes-requested explicitly. The web workbench presents the bound task and plan for the decision.

Control flow
approval.on("approved").to(implement);
approval.on("rejected").to(failed);
approval.on("changes-requested").repair(plan, {
  maxRepairs: 2, feedback: approval.output, exhausted: failed,
});
check.on("failure").repair(implement, {
  maxRepairs: 2, feedback: check.output, exhausted: failed,
});

A repair route needs a finite budget and an exhausted destination. The feedback becomes an input to the repair target. Budgets belong to routes: two different check routes may each permit repairs. Unhandled failure does not continue along a success sequence.

Use a command's successful exit as deterministic evidence. An agent saying “tests passed” is not equivalent to a successful validation node. The bugfix example also has an approval gate to verify why its regression test failed.

6. Declare bounded child work

Use workflow.subagent to define a child role, its input schemas, output schema, and limits. Give a parent access with uses: [repositoryScout]. The parent invokes the exposed subagent tool with a unique request ID and awaits the returned report.

Marking a child optional: false makes its successful report necessary for parent acceptance. workflow.subagentResults(parent, child) binds reports from the accepted parent attempt to a later step. Those report envelopes retain request and artifact identities.

The maintenance example demonstrates the full declaration, required call, and report handoff. Tool names differ in native harness presentation; Kouro provides the declared input schema in the tool description.

7. Compose planning and execution

Fusion: agents improve plans together

Declare every member and the synthesis agent with .agent. Pass unwired handles to .fusion(...).use(plannerA, plannerB). rounds: 2 means two review/revision cycles after the initial parallel drafts. The supported range is 0–10; zero goes straight from drafts to synthesis.

Each stage waits for its members before the next stage starts. Model choices, permissions, and declared subagents follow members through reviews and revisions. Synthesis can use model A, but needs a distinct agent handle and starts a fresh session. The composed output is fusion.output. See feature development or deep research.

Milestones: workflows follow dependencies

Supply a planner output of MilestonePlanType, then call .milestones(...).use(workflowA, workflowB). Plans contain id, title, task, workflowId, and dependsOn. Kouro checks assignments, missing dependencies, and cycles before execution.

Eligible workers accept a string task and require no other inputs. They cannot schedule another milestone plan or run commands in the source checkout. The current maximum is 12 milestones. Ready tasks run up to maxConcurrent; dependents wait for all prerequisites to succeed, receive their results and merged changes, and retain the selected workflow's approval gates.

For greenfield work, commit a baseline and schedule scaffolding before dependent modules. For a language port, specify observable behavior, fixture formats, and parity tests, then schedule integration after the ported components. See spec implementation.

Swarms: models work on one shared task

The built-in Agent swarm view takes a list of 1–8 models followed by one task. Members contribute in parallel; the first listed model synthesizes. An authored swarm uses .parallel, a matching .join, and a separately declared synthesis agent. A swarm does one parallel pass; fusion adds review/revision cycles. See the swarm example.

8. Install and run an example

Download an example archive from the examples page and extract it in your project root. It contains .kouro/EXAMPLE_ID/manifest.json, kouro.ts, and any supporting schema file. Avoid extracting over an existing workflow you have edited.

Terminal
tar -xzf chore.tar.gz
# Edit .kouro/chore/kouro.ts and support.ts for your project.
kouro run chore --profile codex-workspace-write \
  --task "Remove the deprecated cache adapter and update its references"

# Or open the workbench from the same project:
kouro serve

The current project is the default; use --workspace /path/to/project for another repository. A normal kouro run prints a run ID and exits when an approval is pending; review it in the workbench using the same data directory. It does not silently approve the gate.

To let Kouro choose from your existing eligible workflows, use the automatic task CLI. An orchestrating AI can pass the full spec produced by fusion as the task:

Terminal
kouro task workflows
kouro task run --task "$(cat SPEC.md)" \
  --workflow develop --harness claude --model YOUR_AVAILABLE_MODEL
kouro task --help

The --workflow IDs must exist in the current project's .kouro directory. Repeat that option to allow several workers. This CLI generates its own milestone plan; it does not directly execute an arbitrary supplied DAG. Node model selections already pinned by a worker remain pinned.

9. Inspect results and deliver changes

Use the workbench's graph, timeline, and invocation inspector to read actual activity and command output. Fusion split view shows member sessions by stage. Milestone approvals remain ordinary durable waits, and failed prerequisites block their dependents.

Workspace changes stay in private Git worktrees. Dependents inherit completed prerequisites; successful milestone execution combines their changes into the private run worktree. Conflicts fail the merge and retain individual worktrees for inspection. Review the Delivery view and explicitly integrate the result into your project.

For exact authoring signatures and return types, continue to the WorkflowBuilder reference. For executable starting points, open the examples.
